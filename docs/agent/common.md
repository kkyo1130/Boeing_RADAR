# 공통 개발 원칙

- 사용자 요청과 세션에서 이미 합의한 범위를 우선한다. 내부 구현·문서 정리·버그 수정에 반복 승인을 요구하지 않는다. 제품 요구가 모호하거나 외부 계약·범위 변경이 필요할 때만 필요한 결정을 질문한다.
- 현재 구현은 `docs/IMPLEMENTATION.md`, 목표는 `docs/service/overview.md`, 기능 계약과 완료 조건은 `docs/spec/`에 기록한다. 목표를 구현 완료로 보고하지 않는다.
- 변경 전에 Git 상태와 관련 코드를 확인한다. 작업 요청과 무관한 수정·덮어쓰기·자동 리팩터링을 하지 않는다.
- 시간은 UTC ISO 8601, 고도는 feet, 방위는 0–359도를 공통 기준으로 한다. 화면의 FL 단위와 API feet를 명시적으로 변환한다.
- 현재 API는 `backend/app/schemas/` 및 실행 서버 OpenAPI가 구현의 원본이다. 확장 계약은 SPEC-002와 `contracts/`에 먼저 정의하고 소비자와 함께 갱신한다. 계획 문서만으로 기존 API가 지원한다고 가정하지 않는다.
- 값의 관측 시각·지시 ID·유효성·품질·근거를 구분한다. 새 지시에 이전 관측을 무조건 재사용하지 않는다. 재검증은 수정 후 새 관측으로 수행한다.
- 판독 불가와 장치 장애는 수치 불일치가 아니다. `null`/사유/채널 상태로 전달하고 최종 판단 보류는 Backend가 담당한다. 값이 0인 것과 값이 없는 것을 구분한다.
- 생성형 추출 결과는 별도 결정론적 범위·형식·지시 조건 검사로 검증한다. 같은 입력을 쓰는 규칙 검사를 완전히 독립된 안전 채널이라고 표현하지 않는다.
- 조종사에게 재확인을 요청하는 보조 알림만 제공한다. 실제 항공기 제어·자동 설정 변경·검증되지 않은 운항 판정은 범위 밖이다.
- 검증되지 않은 confidence는 모델 점수로 표시한다. 입력 품질과 모델 점수, 확률 보정 여부는 별도 정보다. 불확실성으로 강한 경고를 만들어내지 않는다.
- 실제 카메라·마이크·통신 연동과 fixture/mock 검증을 구분한다. 하드웨어가 없으면 관련 검증을 미실행으로 남기고 파일 기반 검증을 진행한다.
- 기존 backend 테스트를 유지한다. 계약·상태·실패 처리 변경에는 관련 회귀 검증을 추가한다. 문서만 바뀌면 링크·형식·정합성 검사로 충분하다.
- 원본 녹음·영상·모델·DB·비밀 키를 Git에 무심코 추가하지 않는다. 작은 허용된 fixture와 정답 라벨만 추적한다. 예제·로그에 개인 절대 경로나 비밀 값을 넣지 않는다.
- 작업 상태는 TODO 한곳에서 관리한다. 변경 범위와 명령·결과·미해결 사항은 해당 workitem에 남긴다. 같은 정보의 여러 사본을 만들지 않는다.
