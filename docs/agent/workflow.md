# 작업 진행 방식

## 시작

1. 사용자가 지정한 기능/workitem과 실제 Git 상태를 읽는다.
2. 선행 결과를 현재 체크아웃에서 확보했는지 확인하고 TODO 담당·상태를 갱신한다. 사람이 정해진 담당은 역할 제안과 구분한다.
3. 명확한 요청 범위는 바로 진행한다. `draft`는 요구사항 초안이라는 뜻이며 새로운 승인 절차를 강제하지 않는다. 해당 범위의 미정 계약은 먼저 확정하거나 독립적으로 가능한 작업만 진행한다.

## 계획 → 구현 → 검증 → 리뷰

- 계획: 목적, 범위, 데이터 계약, 실패 사례, 관찰 가능한 완료 조건을 정리한다. 기술 미정 사항은 결정이 필요한 작업에만 연결한다.
- 구현: 지정한 workitem을 완료할 최소 변경을 만든다. 새로운 기능 목록 전체를 한꺼번에 자동 실행하지 않는다.
- 검증: 완료 조건별 입력·기대 결과·실제 결과를 기록한다. 영상 재생, 실시간 웹캠, mock 서버 검증을 구분한다.
- 리뷰: 변경과 계약을 대조하고 오래된 값의 정상 처리, 인식 실패의 오류 단정, 단위 변환, 근거 누락, 회귀를 확인한다.
- 완료: 필수 조건이 충족되고 검증 근거가 있을 때만 `done`으로 바꾼다. 기존 Mock 기능은 전체 실제 연동 완료로 표시하지 않는다.

| 상태 | 의미 |
| --- | --- |
| pending | 미착수; 선행 작업 또는 결정 필요 여부는 별도 기록 |
| implementing | 구현 중 |
| verifying | 검증 중 |
| reviewing | 리뷰 중 |
| done | 해당 workitem의 완료 조건 검증 완료 |
| blocked | 필수 정보·환경·선행 결과가 없어 해당 작업 진행 불가 |

작업 예약은 Git 문서의 수정만으로 보장되지 않는다. 담당자와 배정을 확인한다. 의존성이 충족된 서로 다른 파트는 독립적으로 진행할 수 있으나 공유 계약·파일은 한 담당자가 조율한다.

## 역할과 인수인계

planner / implementer / verifier / reviewer는 책임 구분이며 필수 에이전트 호출 순서가 아니다. 단일 세션이 순서대로 수행할 수 있다. 위임 시 WI ID, 스펙 버전, 수정 가능 경로, 선행 결과, 반환할 근거를 전달한다. 자식은 작업을 추가 위임하거나 전체 TODO를 임의 수정하지 않는다.

종료 시 해당 workitem에 변경 파일, 코드 커밋 또는 미커밋 상태, 실행 명령, 결과, 남은 결정과 다음 행동을 남긴다. 결과를 실제로 관찰하지 않고 성공이라고 기록하지 않는다.

## Git

- 통합 후보는 기존 `dev`, 배포/안정 기준은 `main`이다. `develop` 브랜치를 새로 강제하지 않는다.
- 새 기능 작업은 특별한 요청이 없으면 최신 `origin/dev`에서 `codex/<설명>` 브랜치를 만든다. 진행 중인 사용자 브랜치는 임의로 교체하지 않는다.
- 구조 변경은 PR #2로 dev(`436c90c`)에 병합됐다. 당시 구조 이동 기준은 dev와 같았으며 이후 에이전트/스펙과 Vision PoC 변경은 `codex/monorepo-scaffold`의 후속 커밋에 포함한다. 새 작업은 최신 공유 기준과 문서 공유 여부를 확인한다.
- 커밋·푸시·PR·병합은 사용자 요청 및 기존 세션의 권한 범위를 따른다. 명확히 요청한 동작을 다시 확인하지 않는다. 자동 병합·강제 푸시·히스토리 재작성 정책은 만들지 않는다.

## Workitem별 PR
