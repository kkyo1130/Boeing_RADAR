## 실행 계획 · SPEC v34

### 입력·출력과 범위

- 입력: 안내 자격·발생 건 ID·입력 제어·재생 결과.
- 산출물: 단일 음성 큐·완료/중단/취소 기록.
- 계약 원본: [상위 SPEC](../../006-advisory-interface.md#구현-계약과-처리-기준). 공통 필드·단위·ID는 SPEC-002를 따르며 사용자 결정과 기술안을 구분한다.
- 담당 완료 조건: AC-03. 이 WI의 결과만으로 다른 기능의 전체 완료를 선언하지 않는다.

### 선행 산출물과 착수 경계

- SPEC-006-WI-02: 항목별 오류/보류 표시와 선택 근거 패널.

위 산출물이 실제 연결되어야 통합 인수를 완료한다. 계약 초안·fixture로 수행할 설계와 단위 검증은 선행 WI 전체 완료를 기다릴 필요가 없으며, 그 경우 실제 연결 미검증을 명시한다. 이미 완료된 WI는 기존 수행 증거를 유지하고 아래 사례를 소급 실행했다고 기록하지 않는다.

### 처리 순서

현재 자격 검사 → 중복/우선순위 정리 → 재생 → 완료 또는 입력에 양보.

현재 저장소의 기존 모듈을 먼저 확장한다. 위 수정 영역 중 아직 없는 경로는 생성 후보이며 기존 구현이라고 표시하지 않는다. 입력·출력 경계에서 실패 사유와 ID를 보존하고 성공과 미실행을 구분한다.

자체 검토 중 colon ID 파싱, 만료된 예약의 다음 claim 복구, 서버 우선순위 강제, HTTP 오류 status 보존, 미확정 입력 token의 서버 조회 복구·비행 선택 변경 후 원래 입력 소유자의 END 연결을 보완하고 회귀를 추가했다. stop이 onended 성공을 만들지 않는지, 비동기 로딩 뒤 유령 재생·중복 탭 claim·저장 응답 유실·실패/중단의 거짓 완료를 검사했다. API의 최종 완료 접수에서도 현재 자격을 다시 검사한다.

남은 한계는 실제 입력 어댑터 연결/실장비 인수, 원격 생산자만 사용하는 경우 poll 지연, 비로그인 프로토타입의 token/재생 결과 신뢰, JSON/Trace 장기 보관 정책이다. 현재 구현의 실제 실행 계약은 contracts/advisory-v2.md이며 기존 역사 메모의 미정 항목은 위 정책으로 구체화했다.
